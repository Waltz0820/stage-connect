# 一覧ページの読み込み遅延調査

2026-10-29。対象は俳優・作品・シリーズ一覧の日本語版/英語版、計6ページ。**調査のみ。アプリ、DB、インデックス、配置、キャッシュ、本番デプロイは変更していない。**

主因は、全件取得と配役の二重取得、空ページ確認を含む逐次通信、それらを毎回行うキャッシュ設定、FunctionsとDBの地域差の組み合わせ。現在の規模ではDBのSELECT実行自体より、APIの往復待ちが大きい。

## 計測方法と再現条件

- 本番の6経路を各3回、その後検索・ページ送り・性別/形式/配信/推しポイント/並び順を含む10条件をGET。全28件HTTP200・本文あり。日本の作業環境からHTTPS接続を再利用。小標本の中央値であり、利用者全体のp95ではない。
- TTFBは要求開始〜レスポンスヘッダー受信。`mainHtmlMs`は最初に`<main`を含むチャンクを受信するまで。圧縮を指定せずHTMLを取得し、HTML完了時間と描画時間を区別した。
- 本番コミット `e4036295238cdbc2de2b10b37d3420bb37d6a942` と対象一覧/データ取得コードが一致することをGitで確認。Next.js実体は15.5.28。
- 同じ取得関数を別の読取専用Nodeプロセスで実行し、Supabase公開キー/anon権限のAPI回数・結果行・JSON量・経過時間を計測。各取得3回、推しポイント取得1回。これは本番SSRのトレースspanではないため、本番HTTP計測・本番APIログと分けて評価する。
- 代表SELECT5種をEXPLAIN ANALYZE、実API時間をSupabase edge_logs、累積SQL時間をpg_stat_statementsで確認。集計リセットは2025-12-11で、累積統計を今回だけの数値として扱わない。
- キー・認証ヘッダー・個別レスポンス本文は計測JSONへ出力しない。既存のデータ登録作業は中断している。

### 俳優一覧

`lib/stage-connect.ts:getActorList`は全員の姓名・読み・生年月日・性別に加え、一覧では使わない日英プロフィールも取得。`readDirectoryPages`は500→500→176→0件の4回を逐次取得する。その後にページ内で検索・性別絞り込み・10件への切り出しを行う。プロフィール全文の過剰取得と全件走査の通信がある。

### 作品一覧

`getPlayList`は全438作品を取得してから、50作品ずつ9グループへ分け、全4,710配役と俳優名を取得して主要3人を計算する。グループ間は並列だが、各グループのページ取得は逐次。空になるまで継続するため、全件側だけで空レスポンスの確認が9回ある。

日英の一覧ページはこの計算後に検索/絞り込み/ソートを行い、10作品へ切り出した後、`getPlayMainCastSummariesBySlug`で同じ表示用配役を再取得する。後者には作品ID取得1回・配役取得1回・空ページ確認1回の追加がある。

**1作品ごとにAPIを呼ぶ典型的なN+1はない。** ただし、全件分のバッチ取得と表示分の重複取得があり、10カードのために計26回のAPIリクエストが発生している（全てが逐次ではなく、9グループ間は並列）。

### シリーズ一覧

全作品の`id, franchise_id, created_at`を取り、その完了後に198シリーズの日英説明全文等を取得。独立した問い合わせなのに逐次で、`Promise.all`も実際には前半1件だけ。作品数と更新日をNode側で集計し、検索・ソート後に10件へ切り出す。全説明文の取得と逐次通信が改善対象。

### 空ページ確認の扱い

既存ヘルパーが空まで読むのは、Supabase側が要求範囲より少なく返す場合にも欠落させないための設計。単純に「500件未満なら終了」へ変更すると、上限設定次第で女性俳優や後半データが再び欠落する。改善時はDBページング/確定した総件数/Content-Range等で終了条件を保証する。

## DB実行時間とインデックス

| 代表の等価SELECT | 実行時間 | 観測した計画 |
| --- | ---: | --- |
| 俳優500件・姓名/ID順 | 9.58ms | Seq Scan＋top-N sort |
| 俳優の末尾の空確認 | 4.00ms | Seq Scan＋sort、0件返却 |
| 全作品＋シリーズ情報 | 1.90ms | Nested Loop＋Memoize＋franchises主キー |
| 50作品分の配役＋俳優 | 2.79ms | casts_play_id_idx＋Hash Join＋sort |
| シリーズ198件 | 1.66ms | Seq Scan＋sort |

全てメモリ内で処理され、今回の代表計画でディスク読み込み/一時ファイルへの退避は発生していない。EXPLAINはpostgres接続での等価SELECTで、PostgRESTのJSON集約や通信の時間を含まない。対象4テーブルの公開SELECT policyは`true`。

本番edge_logsの直近10分集計では、米国発APIのorigin中央値は約247〜252ms、上流処理の平均は約11〜21ms。これはAPI全体と上流処理の差を示しており、差分全てを純粋な回線RTTと断定はしない。SQLの実行が毎回数秒かかる状態とは異なる。

- `casts(play_id)`、`casts(actor_id)`、人物/作品/シリーズの主キーとslugの一意索引は存在。配役抽出では既存索引が使用されている。JOINそのものを撤去する根拠はない。
- `actors(name,id)`の索引はない。ただし現在1,176行のsortは約10msで、数秒の主因ではない。
- `plays(franchise_id)`のFK索引不足と、`franchises(name)`の重複索引はAdvisorにもある。将来のDB側集計/ページングの設計時に検討し、今回の主因解消として無条件に追加/削除しない。[FK索引の診断](https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys)、[重複索引の診断](https://supabase.com/docs/guides/database/database-linter?lint=0009_duplicate_index)。
- 現在の検索・性別・ジャンル・形式・年順・支持率順・件数集計は、主に全件取得後のNode側で行っている。その部分はDBの索引を追加しても通信件数を減らせない。

## 配置・SSR・キャッシュ

本番Deployment `dpl_BGo2B2EEiJkJiCzkbMCu3zFS6V8X`のFunctionsは`iad1`（米国東部）、Supabaseは`ap-southeast-2`（シドニー）。実APIログにも米国Ashburnからのリクエストを確認。地域差が複数の逐次通信に重なる。[Vercelの地域設定とデータ配置の説明](https://vercel.com/docs/functions/configuring-functions/region)。

対象6ページは`searchParams`を読み、専用のrevalidate設定や共有データキャッシュはない。Supabaseクライアントも通常の`fetch`を渡すだけで、一覧取得関数に`unstable_cache`等はない。[Next.js 15の既定キャッシュ変更](https://nextjs.org/blog/next-15)とも整合する。

全28応答は`x-vercel-cache: MISS`、`Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate`。繰り返しアクセスしてもカタログ取得を避けられていない。詳細ページ側の`revalidate=3600`は一覧へ引き継がれない。

対象一覧に`loading.tsx`はない。データ取得完了まで本文を返せず、遷移/絞り込み時のフィードバックも乏しい。通常のGET検索フォームはドキュメント遷移になるため、応答が来ない間の体感が特に悪い。[Loading UIの仕組み](https://nextjs.org/docs/app/api-reference/file-conventions/loading)。

## クライアント側の切り分けと限界

ブラウザで俳優/作品一覧のフォーム・10カード・ページ送りを確認した。HTMLのDOM要素数は俳優291〜309、作品618〜674、シリーズ505〜565で、全カタログがクライアントへ描画されている構成ではない。

一覧のヒーローは文字とCSS中心。宣言された共通CSS3本はデコード後約296KBで、JavaScriptも共通部が大きい。About/DMM等のCSSが共通レイアウトで読み込まれており、軽量化の余地はある。ただし宣言アセットの総量はnomodule等を含み、ブラウザ実転送量とは異なる。外部の広告/GAもあり、モバイルのCPU・LCPへの影響は今回未定量。

利用できるブラウザ計測APIにはPerformance APIがなく、通常Chromeの取得も最小化状態でできなかったため、**LCP/INP/長いタスク/描画CPUの正確な値は未取得**。HTMLが届くまでの秒単位の待ちは直接測定した事実で、CSS/モーションのせいだと推測して作り直す根拠はない。クライアントの副次的な寄与は、サーバー改善後に実機プロファイルで再評価する。

Vercelログは1時間窓が保持期間境界でエラー、15分窓では該当出力なし。個別SSR内部spanを取れたという扱いはしない。SupabaseのヘルスはACTIVE_HEALTHYで、計測したデータAPIに失敗やスキーマfallbackはなかった。

## 改善案と実施順

1. **作品の配役取得を表示10作品に限定する。** 全作品の検索用基本情報を取る経路と、表示分の主要キャスト取得を分離。現在の初期10件なら26回→約4回の構成にできる。現行の主要3人決定規則・兼役の人物重複除去・日本語/英語名をそのまま使う。既存関数はトップ/配信等からも使うため、全呼び出し先の挙動を変える広い書き換えは避ける。
2. **公開カタログデータへ短い共有キャッシュを設定する。** 現行Next.js 15の`unstable_cache`等で60秒程度から検証。日英で共用できる基本データは共用し、公開カタログだけを対象にする。管理更新/登録後の失効経路と外部MCP経由の更新を考慮し、TTLだけで許容できる鮮度を明示する。投票者固有の情報を混ぜてキャッシュしない。
3. **FunctionsをDBに近い地域へ置く検証を行う。** シドニー候補をPreview等で比較し、cold/warm両方と日本からの体感を再測定。DBの移設を伴う必要はない。今回、地域設定は変更していない。
4. **俳優の不要な日英プロフィール取得を外す。シリーズの独立2問い合わせを並列化する。** まず小さな変更で再測定し、その後に一覧専用の取得項目・集計/ページングを設計する。
5. **一覧の軽いLoading UI/送信中表示を揃える。** SSR・SEO・既存デザインを維持して操作への反応を早くする。実際の取得削減とセットで行う。

次段階のDB側検索/ソート/件数/ページングでは、姓名スペース、NFKC、かな/カナ、英名/slugの現在の検索意味を保持する。日付は文字列の単純sortへ置き換えず、現在の公演期間の比較規則を保持する。検索語・形式・シリーズ・配信・支持率と最小投票数、10件ページ送り、絞り込み後の総件数、JP/EN・canonical/hreflang・既存URLを検証する。1,000行以降の俳優/女性が欠落しない既存回帰条件も引き継ぐ。

改善後の秒数はまだ未計測。上記順序で小さく適用し、同じ28条件とAPI回数・取得量・表示結果を比較して効果を確認する。
