# Stage Connect リノベーション初期診断

2026-10-15。ローカルコード・SQL・既存資料から始めた初期診断。
その後、実DBの主要4テーブルの公開API定義と全行を読み取り、配役の補足表記を調査した。
確認結果と一作品の補完試行は [初回実証結果](renovation-first-pass-results.md) を参照。
制約・索引・RLS・関数の完全な定義と、Vercelの本番設定は引き続き未確認。
相談後の進行案は [リノベーション計画案](renovation-plan.md) を参照。
以下の工事順序は初期案であり、現在の計画では一作品の調査・登録の実証を早い段階に置く。
デザインはGPT側のラフを実装する。その他は既存の骨格を維持したブラッシュアップとし、下記の整理候補をすべて実施する前提にはしない。

## 目的と維持するもの

俳優・作品・シリーズを、配役、出演歴、共演関係で辿れる構想を維持する。
画面の説明文を抑えた設計と、手作業で精査・登録したデータを土台にする。
調査・照合・登録をAIが担いやすくし、人の判断が必要な不一致を明確にする。

既存のIDと公開URL、配役、兼役、出演区分、掲載順を移行時に保全する。
本公演・再演・ライブ、A/B、サポート・ゲスト・声・映像の出演を、移行の都合で統合しない。
不明、非公表、未確認を区別し、資料に記載がないことを不出演と判定しない。

## 情報収集と対象作品の選別

ユーザーの運用方針として、キラハイ（kira-hai.net）を第一参照先にする。
公式サイト、ローチケ、チケットぴあ、ファンサイトなどで不足・不一致を補完する。
キラハイは2.5次元以外の出演作品も掲載するため、詳細収集・登録の前に作品単位で選別する。
原作、企画の位置付け、既存シリーズとの関係を根拠に、対象・対象外・要確認に分類する。
シリーズ内の本公演、ライブ、特別公演などの扱いも記録し、次の作品の判定で再利用する。
境界事例の採否基準は既存DBとユーザーの意図を確認して固め、独自に範囲を拡大しない。
調査、対象判定、既存データ照合、差分作成、登録、登録結果の検証までを一続きの作業にする。
新情報の未確認事項を、手作業で精査済みのデータへ推測で上書きしない。

## 確認した構成と整理候補

| 領域 | コードから確認したこと | 整理の方向 |
| --- | --- | --- |
| アプリ構成 | ルートにVite、`next-app`にNext.jsがあり、公開画面の実装が両方に存在する。Nextの管理画面はルート側のコンポーネントを参照する | 実際の利用箇所を確認してNextを中心に統合。旧ファイルを一括削除する段階ではない |
| 管理画面 | Next側で独自ルート照合とReact Router互換層を使う。管理系の多くで`@ts-nocheck`が有効 | Nextのルートと型付きのデータ操作に段階的に移す |
| データ取得 | `next-app/lib/stage-connect.ts`に俳優・作品・シリーズ・検索・ガイドの取得、集計、表示整形が集まる。英語カラム不在時の再取得処理も残る | 実DBとの対応を確認し、取得・集計・表示整形を分離。生成したDB型と共通の取得処理を使う |
| 公演日程 | `period`と`venue`の文字列を公開画面で分解して日付・都市・会場を表示する。日英で類似処理がある | 原文を残しつつ、公演地・開始日・終了日・会場を構造化する案を検証。年・月のみ判明する公演も扱う |
| 配役 | `casts`は俳優・作品・役名・グループを保持し、同一俳優の複数役を許容する。一方、役名やグループの複数値を文字列から分解する処理もある | 現データの表記を調べてから、役柄・所属・出演区分・別名の分け方を設計。表示文字列を機械的に分割して確定しない |
| 外部取り込み | `external_*`に原文・取得元・照合先・採用状態を保存する土台と、取り込みログがある | 候補保存を活用し、出典・照合・差分・登録の流れをAI作業に対応させる。特定サイト専用の処理と共通処理を分ける |
| 採用処理 | 管理画面で配役追加、候補の採用状態更新、ログ記録を順に実行している | 一部だけ成功する状態を避けるため、採用処理のトランザクション化と再実行時の整合性を検討 |
| 見た目 | 共通CSSに画面ごとの調整と上書きが蓄積している | 見た目の基準を保存したうえで、共通部品と画面固有のスタイルを整理 |
| DB再現性 | `sql`には追加・変更SQLがあるが、主要テーブルの初期作成定義は今回の追跡対象ファイルから見つからない | 実DBから定義・制約・索引・RLSを確認し、再現可能なスキーマと変更手順を整備 |
| 運用資料 | NextのREADMEは検証用・公開画面移行中の説明。現在は管理画面もNextから参照している | 本番の実態を確認し、起動・ビルド・デプロイ・データ投入の手順を更新 |

## 進める順序

1. **現状の基準を作る。** 実DBとVercelの構成を読み取りで確認。作品・俳優・配役の件数、URL、主な関連、代表画面を記録し、復元できるデータ保存を用意する。
2. **実装の責務を整理する。** Nextの実行単位、DBの型、取得・整形処理、管理画面を整理する。初期段階では既存データの意味を変えない。
3. **DB変更案を実データで検証する。** 日程・会場・役柄・出演区分・別名・出典を対象にする。既存IDを保ち、原文と変換結果を比較できる移行を設計する。
4. **AIによる投入経路を整える。** 調査根拠、既存情報との不一致、追加・変更予定を記録する。照合できた情報と未解決事項を区別し、再実行しても重複しない登録処理を用意する。
5. **公開画面を整理する。** 文字の少なさ、情報密度、相互リンク、日英の表示、スマホ操作を保ちながら部品とCSSを整理する。

## 検証する代表例

- テニミュ1st：世代交代、学校、A/B、ゲスト、サポート、兼役、旧芸名。
- 刀ステ：再演、複数役、声・映像出演、歴史上人物、シリーズ間での俳優の共通化。
- 日付が年・月までしか判明していない作品、年非公表の俳優。
- 候補を再取得・再採用した場合、採用処理が途中で失敗した場合。
- 既存URL、配役、俳優別出演数、共演集計、初期HTMLの主要リンク。

## まだ判断しないこと

実DBに欠陥がある、既存データが誤っている、本番が不安定である、という結論は出していない。
ファイル構成の重複や文字列保存だけを理由に全面移行はしない。
本番スキーマと代表データを確認してから、必要な変更範囲を絞る。
