# 再取り込み・採用処理の改修

2026-10-16。[配役プレビュー](cast-credit-preview.md) に続き、情報を増やす前の取り込み経路を改善した。
この工程では本番DBへの書き込み、SQL適用、Vercelデプロイを行っていない。

## 再取り込みで判断を消さない

`external-refresh.mjs` を既存のキラハイ取り込みへ組み込んだ。

- 既存の俳優・作品ID、手動照合の状態・確度、別名、確認メモを維持する。
- 採用済み・無視・保留の候補と、採用先cast IDを再取り込みで変更しない。
- 日程取得を省略した実行や取得結果が空の場合、以前の候補日程・会場を空にしない。
- 既存の照合先を取り込み後の処理でも使う。自動照合の別IDで新規候補を作る経路を修正。
- 照合先がなく未処理のものだけ自動照合を補える。無視した対象を処理対象へ戻さない。
- 更新時には確認時の状態・照合先・日時などを条件に含める。同時編集があれば最新状態から差分を作り直し、3回競合したら停止する。
- 同じ外部データの同時登録による一意性の衝突は、既存行の再取得へ切り替える。

俳優索引の更新は5件ずつ並列処理する。対象行の確認と競合検出が増えるため、旧一括upsertよりAPIリクエスト数は増える。
原文再取得の値と、人が確定した判断を区別するための変更であり、主要テーブルへの直接投入ではない。

`--from-db` は `--write` なしでも読み取りで使用できるようにした。
実DBから1俳優を読み、プロフィールと出演候補8件の取得まで通して `written=0` を確認した。
外部候補の存在とカラムも読み取りで確認：俳優候補1,701件、作品候補823件、配役候補1,520件、履歴568件。
これらは今回の読み取り時点の件数であり、全件を再取り込みした結果ではない。

## 管理画面の整合性

- 状態欄で「採用済み」を選んだ場合も実際の採用処理を通す。状態だけを採用済みにしない。
- 採用済みの状態変更や、採用済みcast IDがある候補の手動照合先変更を防ぐ。
- 手動の作品紐づけ解除は `unmatched_manual` とし、未採用候補を保留へ戻す。次の自動取り込みで直ちに再紐づけしない。
- 新たな手動俳優照合は `matched_manual` として記録する。

以前の手動解除が `unmatched` としか残っていない場合、自動で未照合になった行と区別できない。
既存ログを調べて補う必要がある。新コードだけで過去の意図まで復元済みとはしない。

## 配役・候補・履歴の一括採用

SQL：`sql/2026-10-16_atomic_accept_external_cast_candidate.sql`

候補をロックし、表示時の俳優・作品IDと一致するか確認してから、配役作成・候補の採用済み更新・履歴保存を1回で実行する。
途中で失敗するとすべて取り消される。既存配役がある場合はそのIDへ紐づけ、同じ採用を再実行しても配役と履歴を重複させない。
同じ役に地域・チーム等の条件を持つ既存行がある場合、無条件の行を勝手に追加しない。
声などの元の補足は、渡された役名から削除しない。HTML混入、保留・無視、変更済みの照合先は停止する。

関数は `SECURITY INVOKER`。既存の呼び出し元の権限とRLSを使い、匿名の実行権限は付けない。
既存テーブルのRLSや権限を拡張するSQLではない。
テストではリポジトリ内の外部候補・履歴のSQLと、主要テーブルの最小限の定義から検証環境を作った。
本番の全制約・RLSを再現したものではない。

アプリは一括採用関数を優先し、関数が未導入のDBでは互換処理を使う。
実行エラーや権限エラーが起きたときに旧処理で再実行することはない。
互換処理でも、同じ役の条件付き配役、古い照合先、採用済み候補、重複採用を確認する。
履歴の失敗を「すべて保存済み」と表示しない。
ただし互換処理の複数リクエストは一括取消にならず、配役だけができる可能性が残る。一括性の保証にはSQL適用が必要。

### 本番への適用状態

一括採用の関数は本番の公開API定義にまだ存在しないことを確認した。
API経由でSQL定義を適用する接続は現在用意されていない。
アプリ内で開いたSupabase管理画面は未ログインだった。
ユーザーからChromeでステコネの管理画面へログイン済みと教えてもらい、Windowsの操作経路から接続を試みた。
その画面の読み取り時点で、現在URLの判定ができないというツール側の安全確認により操作が停止した。
ステコネの管理画面へのログインは、SupabaseのSQLエディタへのログインとは別のもの。

適用可能なSQLエディタまたはDB接続が使える段階で、既存テーブル・索引・RLSを照合してSQLを適用し、本番のAPI定義へ反映されたことを確認する。
SQLは配役の書き換えをせず関数だけを追加する。戻す場合は新関数を削除する前にアプリの互換動作を確認する。

## 依存パッケージ

Nextは15系を維持して15.5.14→15.5.28、Reactは19.2.1→19.2.4、Supabaseクライアントは2.101.1へ更新した。
Nextが参照するPostCSSは8.5.30以降へoverrideし、既知の問題のある固定依存を置き換えた。
Nextアプリの `package-lock.json` を更新し、`npm audit` と `npm audit --omit=dev` は0件。
旧Viteアプリ側の依存監査まで完了したという意味ではない。

SQL実行のテスト用に、開発依存として `@electric-sql/pglite` を追加した。
通常のアプリ表示や本番のDB接続に使うライブラリではない。

## 検証

- Nodeの44テストに成功。再取得時の保全、同時編集、同時登録、手動解除、再実行、兼役、条件付き配役の重複防止を含む。
- SQLをローカルのPostgreSQL互換エンジンで実行し、履歴保存を意図的に失敗させても配役・採用状態が残らないことを確認。
- 閲覧者・匿名からの呼び出しを拒否し、既存ポリシーの管理者から採用できることを確認。
- 互換処理で履歴が失敗した場合に部分完了として返し、実際のRPCエラーから互換処理へ逃げないことを確認。
- Nextの本番ビルドでコンパイル・型確認・静的生成を確認。
- 更新後のNext本番モードで日英作品ページと管理画面ルートのHTTP 200を確認。日英の作品名と俳優リンクも初期HTMLで確認した。管理画面の認証済み操作を確認したという意味ではない。

未完了は、本番へのSQL適用、認証済み管理画面での操作確認、デプロイ後の動作確認。
配役の新しい保存形式と日英表示は引き続き別の工程で扱う。
