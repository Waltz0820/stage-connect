## 登録の単位

`sql/2026-10-16_reviewed_actor_registration.sql` の `register_reviewed_work_actor` は、次を一つのトランザクションで処理する。

1. 候補ID・作品URL・配役キー・原文の氏名・俳優URL・出典の指紋・更新日時を照合する。
2. 人物とプロフィールの接点、および投入する項目ごとの根拠を検査する。
3. 必要なら俳優を作成し、確認済みプロフィールと俳優IDの対応を保存する。
4. **当該配役候補だけ**を俳優IDへ紐付ける。未確認の同名候補やURLなしの全候補へ広げない。
5. 登録に使った値・根拠・候補ID・処理キーを履歴に保存する。

途中で履歴保存等が失敗した場合は、俳優・対応表・候補の変更も取り消す。
同じ処理キーでの再実行は登録済みの結果を返し、人物・履歴を増やさない。候補の紐付けが後から訂正されていれば、古い登録要求で戻さず停止する。
処理キーは該当人物の判断を基に作り、別の俳優の調査が進んでファイル全体が変わっても、登録済みの人の再実行を妨げない。
この処理は俳優1名ごとに原子的であり、複数人の全体が一つのトランザクションになるわけではない。途中失敗では完了分と未完了分を記録する。

## 氏名とプロフィールの扱い

新設の `actor_identity_sources` は、確認済みの人物プロフィールURLと俳優ID、その判断根拠を保持する。
同じ確認済みURLが次の配役でも使われた場合、氏名と投入予定の既知項目が矛盾しなければ既存IDを再利用する。この経路では既存俳優の空欄補完や上書きもしない。

対応表にない人が、既存の氏名・読み・slugと衝突した場合は停止する。自動で同名を統合したり、slugに数字を足して別の俳優を増やしたりしない。
同名の別人や改名・異表記を扱うには、別途根拠を付けて判断する必要がある。
別人と確認できた既存候補は、対象ID・名前・生年月日・更新日時と根拠を明示して区別できる。生年月日の違いも両者の資料で確認し、既存人物の状態が変わっていれば停止する。
同音だから無条件に除外する処理にはしない。既存slugを使うことはこの判断でも許可せず、別のURLを明示的に選ぶ。
プロフィールURLの末尾スラッシュや転送先等を勝手に同一視せず、URLの変更・別名の登録は今後の工程に残る。

今回の最終検証では、元の新規候補15名のうちプロフィール接点を確認した8名から、URL判断も済んだ7名を登録対象にした。齊藤来未子は接点を確認済みだが、読み・登録用URLを未確定のまま保持。残り7名は接点が未確認。
出演記録だけの人物を最低限のノードとして登録する経路は別途必要であり、情報不足を理由に削除しない。

## 公開する情報

- 読み・英語表記・生年月日・身長・血液型・性別のうち、項目別の根拠を確認した値だけを投入する。
- 不明な値はnullのまま。profile・profile_enはnullで新規作成する。作文を追加しない。
- URLは `research/bleach2006-2.actor-slugs.json` の個別判断を使用する。名前の漢字から読みを推測せず、確認済みの読み・英語表記を基に選定した。
- 佐藤美貴・井上晴美・岩間健児のslugは、読みからのローマ字化であり、公式英語表記の確認とは区別する。既存の英語表示はname_en未入力時にslugから表示名を組み立てる仕様が残る。
- 林修司も確認済みの読みからURLを選定した。鈴木省吾は同音の既存人物がいるため `suzuki-shogo-1963` と明示判断し、英語名は事務所の綴りから整えた `Shogo Suzuki` を保存する。URLの数字を表示名に混ぜない。
- 履歴と人物出典の対応表は管理者用。一般公開の権限は付けない。

コードは根拠の形式と対象の整合性を検査するもので、URL先の記述の真偽を自動保証するものではない。

## CLI

`next-app/scripts/register-reviewed-actors.mjs` は既定でローカルの差分確認のみ。
元の作品抽出・作品判断・全件保存データから対象の配役行を再構築し、項目別人物調査とURL判断を組み合わせる。

```powershell
# next-appで実行。保存済み候補を用いたローカルの差分確認。
node scripts/register-reviewed-actors.mjs --source-file=<作品抽出JSON> --review=research/bleach2006-2.review.json --research=research/bleach2006-2.actors.json --slugs=research/bleach2006-2.actor-slugs.json --snapshot-dir=<元の全件保存先> --candidates-file=<保存済み候補JSON> --output-dir=<Git管理外の記録先>
```

明示的な `--write` では候補ファイルを使わず、現在の俳優と当該作品の候補を実DBから取得して照合する。
送信する値と要求キーを先に記録し、登録後に結果を記録する。通信断時は確定済みの可能性もあるため、write_pendingの記録を残す。
SQL未適用なら停止し、俳優・紐付け・履歴を別々に書く方式へは切り替えない。CLIは配役を採用しない。

元の作品判断とスナップショットは調査対象の再構築に使う。登録後の再実行でも同じ対象行を復元し、実DBの候補更新日時・指紋・既存人物の競合は関数で再確認する。
管理画面の従来のskeleton作成ボタンを、この新経路へ切り替えたわけではない。認証済み画面の操作確認も未実施。
