## 今回の前提

- テニミュ1stと刀ステの手入力済み配役は、照合品質と表示確認の基準に使う。
- キラハイを第一参照先にし、公式・ローチケ・ぴあ・ファンサイト等で補完する。
- 最初に作品を対象・対象外・要確認へ選別する。2.5次元俳優の出演だけで対象と決めない。
- キラハイに掲載された過去作品の対象範囲を整理し、収録状況を追えるようにする。
- 既存ID、公開URL、配役の区別、登録済みの翻訳を保全する。
- 俳優プロフィールの作文を増やさない。基本情報と出演関係を中心にし、元宝塚など重要な経歴だけを根拠付きの短い補足として残す。詳しい調査記録と公開する情報量は分ける。
- Next.js、Supabase、Vercelを継続使用する前提。構成整理のためだけに技術を入れ替えない。
- 初回の言語対象は既存の日英。追加言語は別途相談する。
- デザインはユーザーがGPT側で作成するラフを基準に実装する。文字の少なさと情報密度を維持する。
- 作品・俳優・シリーズ・配役の骨格を維持する。追加テーブル、ルート再編、管理画面の刷新は、具体的な必要性を確認して個別に判断する。

## 工事の順番

### 1. 現状の基準と設計方針を作る

実DBのスキーマ・制約・索引・RLS、Vercelのデプロイ対象、稼働中のコードを確認する。
ローカルSQLと実DBの違いを整理し、データ保存と復元の手順を用意する。
テニミュ1st・刀ステなどの代表URL、作品・俳優・配役の件数、主要な集計・リンクを記録する。
現行のスマホ・PCと日英の代表画面を比較用に保存し、新しいデザインはGPT側のラフを受けて実装する。

成果物は現行の構成図に相当する説明、変更対象一覧、データ対応表、代表データと画面の確認基準。
既存URLやデータの意味を維持できることを、最初の条件にする。

### 2. 一作品で調査から公開確認まで通す

最初に既存の入力済み公演を調査し、得られた配役と登録済みの配役を比較する。
通常出演のほか、兼役・ゲスト・サポート・声・映像出演などを照合できるか確認する。
差がある場合は根拠を残し、既存データを自動で調査結果へ置き換えない。

続いて、対象範囲が明確な他シリーズの未充足作品を一つ選び、次を通す。

1. 対象作品か判定し、シリーズ・初演再演等の位置付けを確認する。
2. 公演・配役・俳優の情報を収集し、不足・不一致を補完する。
3. 既存IDへ照合し、追加・補完・変更候補と未解決事項を作る。
4. 根拠付きで確定できる差分を登録する。人の判断が必要な点はまとめて相談する。
5. 日英の表示と固有名詞を確認し、作品・俳優・シリーズの各画面と集計を検証する。

この工程に必要な型・取得処理・登録処理を先に整える。
試行結果から、人が介入した箇所とその理由、情報源の不足、必要なDB変更を整理する。
AIが実際に入力負担を減らせるかを、全面改修の早い段階で確認する。

### 3. 実証した処理を運用の中心にする

一作品の試行で必要と分かったDB変更を、原文・旧IDとの対応を保って段階的に実施する。
公演地別日程、役柄、出演区分、芸名・別名、出典等は、実データを見て必要な範囲で構造化する。
過去データに根拠URLが残っていない場合、新たに確認した根拠と区別して記録する。

採用処理は、一度の登録が途中までしか反映されない状態や、再実行時の重複を防ぐ。
変更単位と履歴を残し、修正箇所を追えるようにする。
管理画面は既存の入力・編集機能を活かし、作品単位の不足・調査中・未解決の状態など、必要な補助機能を追加する。
AIの照合と登録は構造化した処理で実行し、人が確認・訂正する画面も維持する。

実行構成の依存関係を把握し、型チェックと共通処理を変更対象から整える。
旧Vite側のファイルや管理画面の互換層は本番利用と改修への影響を確認し、整理が有効な箇所から扱う。
初期段階ではVercelのルートディレクトリ変更などをまとめて行わない。

### 4. 公開画面・多言語・視聴導線を揃える

GPT側で作成したラフをもとに、作品・俳優・シリーズの画面を実装する。
必要な表示データと既存の相互リンクをラフに対応付け、共通部品を整える。
翻訳は同じ俳優・作品・役柄を参照し、表記揺れや未翻訳を追えるようにする。
日英のURL対応、メタデータ、ページ言語、サイトマップと主要リンクも確認する。

配信情報は公演・配役の確定情報とは別に更新する。
DMM APIは取得できる項目と対象サービスを確認してから利用範囲を決める。
作品名だけで自動紐付けせず、公演・キャスト・収録内容を照合する。
配信未確認と配信なしを区別し、視聴条件・リンク先・確認時点を管理する。
U-NEXT等の掲載・収益化条件も確認したうえで視聴先を追加する。

送客は作品・言語・サービス・ボタン位置を区別して計測する。
サイト側のクリックとアフィリエイト側のクリック・成果は別の指標として扱う。
流入ページの目的を分け、導線変更前後で評価する。全体CVRの低さも改善対象に含める。
CVR 1%は会話中の仮目標であり、業界標準や達成保証として扱わない。

### 5. シリーズごとに収録を広げる

対象一覧に対して、収録済み・不足・対象外・要確認を管理する。
一シリーズずつ作品と配役を埋め、日英・視聴情報・関連リンクの状態を確認する。
既存データの欠落を補う作業と、新作追加の作業を同じ手順で回せるようにする。
新たな境界事例は採否の理由を記録し、次の調査で再利用する。

## 完了を判断する基準

- 既存の作品・俳優・シリーズURLと主要な相互リンクが保たれる。
- 代表公演の配役・兼役・区分・掲載順と、出演数・共演数を比較できる。
- 登録の再実行で重複せず、失敗後の状態を確認・復旧できる。
- 調査した根拠、採用した差分、未解決の点を辿れる。
- 作品一つを増やすために、ユーザーが全件を調べ直して手入力する必要がなくなる。
- 日英で主要情報と回遊経路が揃い、未翻訳・表記未確認を把握できる。
- 視聴ボタンの案内と実際のリンク先・視聴条件が対応する。
- スマホ・PCで代表画面を確認し、影響するビルドと必要な回帰確認が通る。
