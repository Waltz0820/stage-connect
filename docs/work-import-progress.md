## 実装

- `next-app/lib/work-import-plan.mjs`：作品の抽出結果、主要テーブルの全件スナップショット、根拠付きの個別判断を照合する。
- `next-app/scripts/prepare-work-import.mjs`：JSONの登録準備案と、読むためのMarkdown一覧を生成する。
- `next-app/research/bleach2006-2.review.json`：実際に参照した作品の範囲判定、作品ID、改名・別人の判断と根拠。
- `npm run test:work-import`：11テスト。原文・兼役・アンサンブル・旧名・同音別人・条件付き配役・重複・古い判断・既存情報の保全を検証。

候補は「既存を維持」「配役追加案」「新規俳優の準備」「保留」に分ける。新規俳優の準備は人物作成の確定を意味しない。キャスト欄で名前だけ確認できた人は、プロフィールや別名の調査が未完了と分かる状態で残す。

作品の対象判定や同一公演の照合が未完了、日程の年が矛盾、抽出できない行がある場合は、作品全体を保留へ回す。個別の判断は名前だけではなく確認時のID・名前・更新日時も照合する。

## 手入力を保全する扱い

- 既存配役を上書きしない。掲載順・主役フラグ・手書きのnote等をそのまま残す。
- 同じ役に「声」「福岡公演」「日替わりゲスト」等の補足があれば、無条件の配役を追加せず確認対象にする。
- 兼役を一人一役へ縮めず、役名と区分を別々に維持する。中黒で勝手に分割しない。
- `plays.credits` に同じ人名が残る場合も、別経路の出演記録と二重になる可能性を示す。
- 出典の並びは `sourceOrder` として保持するが、公式の掲載順位と決めつけて `billing_order` へ投入しない。
- 出典に出てこない既存配役も削除しない。
- 作品ごとの改名確認を翻訳・表記の辞書へ混ぜない。同じ読みやURLから別人を結び付けない。

スナップショットは保存時の件数・全件のID重複・SHA-256を確認する。JSONの編集やファイル不足を検出し、状態の違うデータで準備案を作らない。出典・レビュー・DB内容の指紋を準備案に残す。将来の登録処理では最新DBとの再照合が必要であり、この指紋だけで同時更新を防げるわけではない。

## 保存経路で見つかった不足

本番のAPI定義を読み取り、既存の `external_cast_candidates` では `source_actor_url` が必須で、出演区分用のカラムもないことを確認した。
俳優別ページを持たない出演者や、役名を持たないアンサンブルを、現在の取り込み経路へそのまま流せるとは扱わない。作品URLを俳優URL欄に代入したり、アンサンブルを役名へ混ぜたりすると出典・人物・区分が崩れる。

今回の準備案では俳優URLなしをnullのまま保持し、役名と区分を分けている。次の保存経路の改修では、この情報を外部候補から採用まで落とさず渡す必要がある。
前工程の一括採用関数も本番APIには未導入であることを再確認した。

続報：上記の不足に対応する [候補保存・区分付き採用](work-candidate-storage.md) を実装し、ローカルDBで22行の保存と既存俳優7名への採用を検証した。実DBへの導入はまだ行っていない。

